Testes Avançados: JUnit, Cobertura (JaCoCo) e Análise Estática (SonarCloud)

JUnit Jupiter com intenção, relógio determinístico, o que a cobertura realmente mede, configuração de gate com JaCoCo, e como o SonarCloud e o Quality Gate entram no pull request.

1. Cenário de qualidade — E2 (Sessão e Acesso)

Regra crítica: token expirado nunca libera acesso, mesmo quando a assinatura está ativa. Token ausente, inválido ou revogado também é negado. Somente token válido e não expirado permite continuar para as demais decisões de autorização.

EntradaDecisãoMotivo estável
AusenteNegarTOKEN_AUSENTE
Assinatura inválidaNegarTOKEN_INVALIDO
Expiração ≤ agoraNegarTOKEN_EXPIRADO
RevogadoNegarTOKEN_REVOGADO
Válido e vigenteProsseguirsem negação

3. Organização por contexto

class AutorizadorSessaoTest {
  private final Instant agora = Instant.parse("2026-09-21T10:00:00Z");

  @Nested
  @DisplayName("quando o token está expirado")
  class TokenExpirado {
    @Test
    void negaMesmoComAssinaturaAtiva() {
      var token = tokenComExpiracao(agora.minusSeconds(1));
      var decisao = autorizador.avaliar(token, assinaturaAtiva(), agora);
      assertAll(
() -> assertFalse(decisao.permitido()),
() -> assertEquals(TOKEN_EXPIRADO, decisao.motivo())
      );
    }
  }
}

O instante é dado explícito. A assinatura ativa existe justamente para provar a precedência da expiração do token.

4. Teste parametrizado de limite

@ParameterizedTest(name = "expira em {0}s → válido? {1}")
@CsvSource({ "-1, false", "0, false", "1, true" })
void respeitaLimite(long deslocamento, boolean esperado) {
  var agora = Instant.parse("2026-09-21T10:00:00Z");
  var token = tokenComExpiracao(agora.plusSeconds(deslocamento));
  assertEquals(esperado, validador.estaValido(token, agora));
}

A trinca imediatamente antes / no limite / imediatamente depois captura erros de < versus <=. Use @ValueSource para uma entrada, @CsvSource para pequena tabela e @MethodSource para objetos de domínio.

5. Relógio determinístico

Chamar Instant.now() dentro da regra prende o domínio ao ambiente. Injete Clock ou passe o instante como argumento.

public final class ValidadorToken {
  private final Clock clock;
  public ValidadorToken(Clock clock) { this.clock = clock; }
  public boolean estaValido(Token token) {
    return token.expiraEm().isAfter(Instant.now(clock));
  }
}

var clock = Clock.fixed(
    Instant.parse("2026-09-21T10:00:00Z"), ZoneOffset.UTC);

Produção injeta Clock.systemUTC(). Testes injetam Clock.fixed. Não há espera, corrida ou dependência de timezone local.

6. O que a cobertura mede

  • Instruções/linhas: quais unidades executáveis foram alcançadas.
  • Branches: quantos resultados de decisões foram executados.
  • Complexidade: aproxima caminhos independentes e ajuda a encontrar regra difícil de testar.

Cobertura é condição necessária de observação, não prova de assert correto. Um teste que executa o ramo e não verifica sua decisão aumenta cobertura sem reduzir risco. Antiobjetivo: escrever testes triviais de getters ou excluir classes relevantes apenas para atingir o percentual.

7. Configuração JaCoCo

Na release estável 0.8.15: prepare-agent instrumenta a execução; report gera HTML/XML; check interrompe verify abaixo das metas.

<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.15</version>
  <executions>
    <execution>
      <goals><goal>prepare-agent</goal></goals>
    </execution>
    <execution>
      <id>report-and-check</id>
      <phase>verify</phase>
      <goals><goal>report</goal><goal>check</goal></goals>
      <configuration>
<rules><rule>
  <element>BUNDLE</element>
  <limits>
    <limit><counter>LINE</counter><value>COVEREDRATIO</value><minimum>0.80</minimum></limit>
    <limit><counter>BRANCH</counter><value>COVEREDRATIO</value><minimum>0.70</minimum></limit>
  </limits>
</rule></rules>
      </configuration>
    </execution>
  </executions>
</plugin>

Não configure Surefire com forkCount=0: isso impede o javaagent do JaCoCo de registrar cobertura.

8. Ler e usar o relatório

Execute ./mvnw verify e abra target/site/jacoco/index.html. Navegue de pacote para classe e linha.

  • Comece pelas regras de autorização e sessão, não pelo percentual total.
  • Linha vermelha: avalie risco, código morto ou cenário ausente.
  • Branch amarela: identifique o resultado não executado.
  • Leia o teste correspondente: há assert que prova o oráculo?
  • Atualize a RTM com o caso de teste, não com uma promessa genérica de cobertura.

A meta global 80/70 é piso. Classes críticas podem justificar um critério mais alto e específico.

9. SonarCloud / SonarQube Cloud

A análise estática procura padrões de bugs, vulnerabilidades, riscos de manutenibilidade, duplicação e outros problemas sem executar o sistema. Ela complementa testes dinâmicos.

Onboarding seguro:

  1. Importe o repositório e selecione análise baseada em CI para o projeto Maven.
  2. Configure sonar.organization e sonar.projectKey no pom.xml.
  3. Crie SONAR_TOKEN nos GitHub Actions secrets; nunca passe valor literal.
  4. Defina "novo código" e revise o Quality Gate.
  5. Confirme decoração no pull request e check exigível.

Não mantenha análise automática e análise pela CI ao mesmo tempo sem intenção: resultados duplicados confundem diagnóstico.

10. Pipeline de análise

- uses: actions/checkout@v6
  with:
    fetch-depth: 0
- uses: actions/setup-java@v5
  with:
    distribution: temurin
    java-version: '21'
    cache: maven
- name: Testar e analisar
  env:
    SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
  run: ./mvnw -B verify \
       org.sonarsource.scanner.maven:sonar-maven-plugin:sonar

O scanner Maven lê o relatório XML do JaCoCo produzido no build. fetch-depth: 0 fornece histórico para análise mais relevante. Pull requests de forks podem não receber secrets; planeje o workflow sem expor token.

Quality Gate: responde se o novo código pode ser integrado segundo condições acordadas; não é uma nota absoluta de arquitetura.

11. Estratégia de Quality Gate

Trate legado e novo código de forma diferente. O projeto tem metas globais de 80% de linhas e 70% de branches; o novo código não deve piorar segurança ou manutenibilidade.

  • Nenhum bug ou vulnerabilidade crítica nova.
  • Cobertura suficiente no novo código, especialmente regras E2.
  • Duplicação controlada no novo código.
  • Issues revisadas: corrigir, aceitar com justificativa ou marcar falso positivo com evidência.

Não marque issue como falso positivo para "ficar verde" sem compreender o fluxo. O gate só tem valor se a decisão for confiável.
