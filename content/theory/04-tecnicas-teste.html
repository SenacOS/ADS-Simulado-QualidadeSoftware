Técnicas de Projeto de Teste: Caixa Preta, Branca, Cinza e Cobertura

Caixa preta, caixa branca, caixa cinza, critérios de cobertura e as técnicas clássicas de projeto de teste — partição de equivalência, valor limite e tabela de decisão — demonstradas com código Python/pytest.

1. Com que olhos você olha o software

Toda técnica de teste responde a uma pergunta anterior: você pode ver o código? A resposta muda o que você consegue enxergar — e o que continua invisível.

Caixa preta

Base: a especificação. Você conhece entradas, saídas e regras de negócio; o código é opaco por escolha. É o olhar de quem usa — e também de quem ataca.

Acha bem: requisito mal implementado, regra errada, validação ausente, funcionalidade faltando.
Não acha: o caminho de código que nenhum teste executa.

Caixa branca

Base: o código. Você olha o fluxo de controle e pergunta por quais ramos ainda não passou. É o olhar de quem escreve — o mais fácil de se enganar: você tende a testar o que implementou, não o que foi pedido.

Acha bem: ramo nunca executado, código morto, condição impossível.
Não acha: o requisito que ninguém escreveu — não há linha para cobrir.

Caixa cinza

Praticada em teste de API: você chama pelo contrato, como um cliente externo, mas escolhe os casos sabendo o que existe atrás. É o modo predominante de teste de API na maior parte do semestre.

2. Critérios de cobertura

O mesmo trecho de código, medido por três réguas diferentes:

if (token != null && !token.expirado()) { liberarAcesso(); }
CritérioExigeTestes mínimos
Comando (linha)Cada linha executada ao menos uma vez1 — só o caminho feliz
Ramo (decisão)A decisão avaliada como verdadeira e como falsa2 — inclui o caso que nega acesso
CondiçãoCada operando avaliado V e F isoladamente3 — token nulo e token expirado são bugs distintos
Cobertura mede execução, não verificação

Um teste sem asserção soma cobertura e não protege nada. Use cobertura para descobrir o que falta testar — nunca como nota.

3. Técnicas de projeto de teste em caixa preta

  • Partição de equivalência — entradas tratadas do mesmo jeito formam uma classe; teste uma por classe. Ex.: plano free, premium, inválido.
  • Análise de valor limite — o defeito mora na fronteira; teste no limite, logo antes e logo depois. Ex.: sessão de 30 min em 29:59, 30:00 e 30:01.
  • Tabela de decisão — quando condições se combinam, monte a tabela e cubra cada regra. Ex.: logado? × assinante? × conteúdo pago?

4. As técnicas em código: acesso.py e test_acesso.py

A regra sob teste:

PLANOS = ("free", "premium")
LIMITE_SESSAO_S = 1800  # 30 minutos

def pode_assistir(sessao, conteudo):
    if sessao is None or sessao.idade_s > LIMITE_SESSAO_S:
return "SESSAO_INVALIDA"
    if sessao.plano not in PLANOS:
return "PLANO_INVALIDO"
    if conteudo.premium and sessao.plano != "premium":
return "ASSINATURA_NECESSARIA"
    if sessao.renovacoes > 3:
return "SESSAO_INVALIDA"
    return "LIBERADO"
Repare no último if

Ele não está em nenhum requisito. Nenhum teste de caixa preta chega até ele — só o relatório de cobertura denuncia sua existência. Achar código assim é exatamente o que a caixa branca faz bem.

As três técnicas aplicadas com pytest.mark.parametrize:

# 1. Particao de equivalencia
@pytest.mark.parametrize("plano, esperado", [
    ("free",    "ASSINATURA_NECESSARIA"),
    ("premium", "LIBERADO"),
    ("pirata",  "PLANO_INVALIDO"),
])

# 2. Analise de valor limite
@pytest.mark.parametrize("idade_s, esperado", [
    (1799, "LIBERADO"),
    (1800, "LIBERADO"),
    (1801, "SESSAO_INVALIDA"),
])

# 3. Tabela de decisao (logado, assinante, premium, esperado)
REGRAS = [
    (False, False, False, "SESSAO_INVALIDA"),
    (True,  False, False, "LIBERADO"),
    (True,  False, True,  "ASSINATURA_NECESSARIA"),
    (True,  True,  True,  "LIBERADO"),
]

Medição: pytest --cov=acesso --cov-branch --cov-report=term-missing. O --cov-branch acrescenta a medição de ramo; nenhuma ferramenta padrão mede cobertura de condição de graça — é decisão de projeto de teste da equipe.

5. Provar que o teste protege: mutação na unha

Cobertura alta não significa proteção. O experimento, um de cada vez:

  1. Trocar > LIMITE_SESSAO_S por >= LIMITE_SESSAO_S. Deve falhar apenas o caso 1800 — é a análise de valor limite fazendo o trabalho dela.
  2. Trocar a condição de conteúdo premium por if False:. Deve falhar o caso free + premium.
  3. Escrever um teste que chama pode_assistir e não tem nenhum assert. Ele passa, soma cobertura e não falha em nenhuma das mutações acima — o defeito mais comum em projeto com meta de cobertura.
Regra da casa

Apague a regra, rode a suíte. Se não ficar vermelha, aquele teste não está protegendo nada.
